# v0.7 고래 알림 재생 검증

대상: 로컬 SQLite 알림 이력의 2026-10-10 UTC 하루. 읽기 전용으로 조회했으며
실제 Telegram·외부 API 호출, DB 수정, 서버 재기동은 하지 않았다.

| 항목 | 결과 |
|---|---:|
| 기존 Telegram 고래·대형 거래 발송 기록 | 20 |
| 저장 payload에서 검증 체결로 표시 | 19 |
| 같은 지갑·코인·방향의 직전 발송 후 5분 이내인 건 | 4 |
| 한 지갑·코인·방향 조합에서 가장 많은 발송 수 | 6 |
| 새 규칙으로 재생 가능한 건 | 0 |
| 재생 불가 | 20 |

20건 모두 당시 변화 유형과 전후 수량이 저장돼 있지 않다. 제목, 금액 또는
발송 시각으로 이를 추정하지 않았다. 따라서 새 규칙의 발송 건수, 중요 이벤트
누락, 실제 지연은 **미측정**이다. 검증 체결 표시는 저장값이며 체인 재검증 결과가
아니다. 앞선 롤링 로그 검토 14건과 달리 이 표는 DB에 저장된 해당 UTC 일자의
전체 발송 기록을 사용한다.

## 고정 테스트 표본

- 같은 5분 구간, 이어지는 수량, 서로 다른 거래 해시: 이벤트 2건 → 후보 1건.
  60초 평가 주기의 이 표본에서 마지막 관측 후 후보 선정까지 120초.
- 두 이벤트가 인접한 5분 구간에 위치: 이벤트 2건 → 후보 2건. 구간 경계에서
  연속 발송될 수 있다는 점을 확인했다.
- 기존 선별 테스트에서 방향 전환 우선 처리, 겹친 거래 해시·미검증·불연속 수량
  제외를 확인했다.

재생은 저장된 관측에 대한 **후보 선정**만 계산한다. 실제 이전 정책을 재현하거나
Telegram 발송 한도, 네트워크 지연, 당시 미발송 후보를 복원하지 않는다.

## 재실행

`backend/`에서 `python -m scripts.replay_whale_alerts hyperpulse.db --day 2026-10-10`.

다음은 별도 비발송 수집으로 **선별 전 전체 후보와 제외 이유**를 확보하는 것이다.
최소 24시간 표본에서 방향 전환·대규모 축소 누락, 구간 경계 반복 및 관측→선정
지연을 확인한 뒤 5분·10%·200만 달러 기준의 조정 여부를 결정한다. 이번 검증만으로
발송 감소율을 주장하거나 운영 기준을 바꾸지 않는다.

## 로컬 비발송 관찰

2026-11-14 20:07 KST에 24시간 관찰을 시작했다. 기존 DB는 지갑 명단과
저장된 계정 규모를 읽는 데만 사용한다. 상위 30개 지갑을 120초 간격으로
조회하고 별도 DB와 JSONL에 기록한다. 첫 주기는 30/30 성공이며 포지션
기준선을 만드는 단계라 후보 수를 평가하지 않는다.

`backend/`에서 실행 예:
`python -m scripts.observe_whale_alerts --roster hyperpulse.db --output logs/whale-observation-new.jsonl --hours 24 --interval 120 --wallets 30`.

관찰기는 HTTP 서버를 열지 않고 Telegram·LLM·랭킹 갱신을 실행하지 않는다.
기존 이벤트 한정 fills 조회 예산을 유지한다. 기록의 reference class는
저장된 지갑 규모를 사용한 분류 결과이며 과거 실제 발송 수가 아니다.
selection은 한도·쿨다운·전송 성공을 반영하지 않은 신규 선별 후보다.
절전·수집 오류는 시간 및 coverage 기록에서 확인한다.
